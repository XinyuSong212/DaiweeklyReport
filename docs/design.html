DaiweeklyReport · 设计文档

没做什么，为什么

一个写日报周报的工具，但它真正在做的事是抢救决策：从 Claude Code 的对话记录里，把你否掉的方案、被约束逼出的取舍、还没想清的问题捞出来，在它们消失之前存成结构化日志。

01问题不在素材，在推理

写日报周报的常见诊断是"记不住"——周五想不起周一干了什么。按这个诊断做出来的工具就是素材聚合器：拉 git、拉日历、拉 issue，拼成一份流水账。

但流水账正是绝大多数日报周报失败的样子。读者（你的 leader）从"重构了支付重试逻辑"里读不出任何东西：他不知道你考虑过什么、为什么否掉、卡在哪。缺的不是素材，是推理。

而推理有个要命的性质——它几乎不落盘。

git 记录着

你做了什么。commit 是决策的结果：最终选中的那条路，以及它改了哪些文件。

git 不记录

你没做什么。被否掉的方案、否掉的理由、逼你这么选的约束——决策的过程，一行都没有。

对话记录着

两者都有。你说"不行，加全局锁会把结账串行化"的那一刻，理由和被否的方案同时在场。

所以这个工具的数据源选择不是为了方便，是因为对话记录是决策过程唯一的留存地。而它默认 30 天后就被清理掉了。

02让报告读起来像思考的五个要素

对比同一件事的两种写法，长度几乎一样：

流水账可被追问的写法
Refactored the payment retry logic (#123) Traced the 4% checkout failure rate to non-idempotent retries, not the gateway timeouts we had assumed. Considered a global checkout lock and rejected it: serializing every checkout would have cost ~3x p99 latency to buy a property we could get locally. Shipped per-request idempotency keys instead (#123); failure rate is 0.6% after two days.

差别可以拆成五个要素。关键在于：五个里有四个只存在于对话里，git 只能供给最后一个。

#要素来源
1最初的判断，以及什么纠正了它你早期提问的措辞
2否掉的方案 + 否掉的理由你表达否定的消息；AskUserQuestion 里没被选的选项
3真正驱动决策的约束你补充上下文的消息
4尚未想清的问题你没被回答的提问
5结果，可量化git / PR / 指标
第 2 项承载最大权重，而它在普通日报里几乎从不出现

这正是流水账读起来像流水账的原因：它描述了一条路径，却没有显示这条路径是被选中的。一份报告能不能被追问，取决于它有没有第 2 项。

04实现：怎么从 JSONL 里分出"你说的话"

transcript 每行一个事件，但 type: "user" 同时覆盖三种完全不同的东西：你真正敲的话、喂回模型的工具返回、以及子 agent 的 prompt。只有第一种是思考。

def is_human_prompt(entry):
    if entry.get("type") != "user":        return False
    if entry.get("isSidechain"):           return False   # 子 agent，由 agent 撰写
    if "toolUseResult" in entry:           return False   # 披着 user 外衣的工具输出
    origin = entry.get("origin")
    # 老版本 transcript 没有 origin 字段；缺失不等于非人类
    if isinstance(origin, dict) and origin.get("kind") not in (None, "human"):
        return False
    return True

分出来之后，按可靠度分四档提取信号。排序不是随意的——它决定了模型该按什么顺序读：

档信号是什么，为什么可靠
① choices 最硬。AskUserQuestion 的 toolUseResult 里同时存着你选的答案和没被选的选项及其描述——一次带着未选路径的、被记录下来的取舍。几乎必然构成一条 journal 条目。
② pushbacks 价值最高、最易腐。你否定或改向的消息，配上被否的那段提议（responding_to，取 assistant 那一轮末尾 900 字符，因为收尾的结论才是你在回应的东西）。
③ endorsements 你认可的消息。单独一般不成条目，它补完由 ① 或 ② 起头的那条——告诉你最终走了哪条路。
④ prompts 其余全部。每个 session 的第一条 prompt 常常比后面任何一句都更准确地陈述了问题。
刻意的不对称：脚本求召回，模型求精确

正则分不出"好，继续"和"好，这个设计对"——只有带上下文的读者能分。而漏掉一条 pushback 在 transcript 过期后不可恢复，多一条误报只花模型一行阅读。所以分类器故意过度触发，脚本 docstring 和 SKILL.md 都写明了禁止为降噪而收紧它。

06脚本接口

两个脚本都能脱离模型独立运行，输出 JSON 或可读的 Markdown 摘要。

collect_conversations.py说明
--days N以今天结尾的窗口，默认 1。日界按本地时区切，transcript 存的是 UTC。
--since / --untilYYYY-MM-DD，两端含。
--project SUB对 project 目录名做子串过滤。
--include-orphaned把被搁置的 .orphaned- 副本也扫进来。会导致 prompt 重复，默认关。
--format json｜mdmd 给人读，json 给程序。
输出{window, totals, sessions[]}；每个 session 含 prompts / pushbacks / endorsements / choices。
collect_git.py说明
--repo PATH可重复；缺省读 config.json 的 repos。
--author EMAIL可重复；缺省读 config.json 的 author_emails，再退到 git config user.email。
--all-authors不按作者过滤。
--include-merges默认排除 merge commit。
输出{window, repos[]}；每个 commit 含 sha / ts / subject / body / pr / files / insertions / deletions。
这个脚本本来被当成简单的那一半，结果藏了两个静默丢数据的 bug

一、日期窗口。git log --since=2026-09-15 不等于当天 00:00:00——git 的 approxidate 会把缺失的时分秒补成当前时刻。实测：时钟 00:24:48 时，一个 00:24:32 的 commit 被滤掉了。早上跑日报会悄悄丢掉当天凌晨的全部提交。修法是始终传显式的 T00:00:00。

二、numstat 错位。--numstat 的统计块打印在格式化头部之后，所以记录分隔符放在格式串末尾时，每条 commit 的文件统计被切到了下一条记录的开头，全部 commit 都报 +0/-0, 0 files。修法是把分隔符前置。

两个都不抛异常、返回干净的空值。同一个窗口修完从 0 commits 变成 1 commit / 11 files / +1132。"跑起来没报错"恰恰是这两个缺陷的外观。

07署名诚实：这是设计约束，不是免责声明

素材来自和 AI 的对话，所以有个绕不开的问题：把对话里的内容写进交给 leader 的周报，边界在哪？

划法是：记录决定了什么、为什么——"chose per-request keys over a global lock, since the lock would have serialized checkouts"。这个判断确实是你做的，不管选项是谁措辞的。但不把模型的分析原样搬进报告当成你自己的论述。两条可执行的推论：

  • 每条 journal 条目必须有 evidence。只靠你从未回应过的 assistant 文本支撑的条目，不算决策，直接丢弃。
  • 你的措辞和模型的措辞不一致时，以你的为准。

判据很直接：你 leader 对报告里任意一行追问一句，你都得答得上来——因为那确实是你定的。

这套约束在本仓库自己的 journal 里已经生效过一次。「日报摄取 / 周报消费」那条决策是模型提出、用户未明确表态只是继续推进的，条目里如实写了：

"evidence":[
  {"kind":"your_words","ts":"2026-09-15T00:18:10+00:00","quote":"你开发的咋样了？"},
  {"kind":"note","quote":"Proposed in-session; user proceeded without objection
                          rather than endorsing explicitly. Weak signal —
                          recorded as such."}]

日报末尾也标了当天各条目的证据强度。写成强证据会好看一点，但一问就穿帮。

08数据源的四条边界

整个设计压在 transcript 上，所以这些边界经查证后写进了 SKILL.md 和 README。先说成立的部分：~/.claude/projects/<project>/<session>.jsonl 是"full conversation transcript: every message, tool call, and tool result"，本地明文，不截断、不摘要。

边界 01

默认保留 30 天

超过 cleanupPeriodDays（默认 30，最小 1）即被删除。这是能回溯的硬上限，也是日报必须每天跑的原因。在 Claude Desktop / Cowork 里最后续过的 session 默认豁免。

边界 02

只覆盖本地 CLI session

网页版和其他远程 session 跑在临时 VM 里，transcript 不落到你机器上。这类工作对本工具完全不可见——journal 显得单薄时，先查这一条，再怀疑挖掘失效。

边界 03

搁置副本会重复计数

session 的旧副本存为 <session>.orphaned-<ts>-<suffix>.jsonl，后缀也是 .jsonl，会被 glob 扫中。实测会让素材整体翻倍，现已默认跳过。

边界 04

不加密，而且什么都录

某个工具读了 .env、某条命令打印了凭据，那个值就明文在 transcript 里，也就可能流进 journal。所以 evidence 绝不能粘未读过的原始片段。

在仓库里对 Claude Code 说「写今天的日报」或「写本周周报」，skill 自行触发。脚本也可单独跑：

python3 .claude/skills/daily-weekly-report/scripts/collect_conversations.py --days 1 --format md
python3 .claude/skills/daily-weekly-report/scripts/collect_git.py --days 7 --format md --repo .

报告用英文写，对话可以是任何语言；证据引文保持原语言。

已知缺口

  • 没有任何机制保证日报每天跑，而周报依赖它。cron 或 SessionStart hook 是明显的下一步，尚未实现。
  • 认可 / 否定的模式是手写的，只覆盖中英文。
  • 网页版 Claude Code 的对话无法挖掘。若大部分工作在那边发生，实际覆盖率比看起来更差。
  • 分类器的松紧只能拿真实使用数据校准。在校准之前就自动化，等于把未验证的判断固化下来。
